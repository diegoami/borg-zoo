# Borg zoo

Seed-suite comparisons of Angband Borg versions and configurations, run
headless on GitHub Actions and published as statistics tables on
[GitHub Pages](https://diegoami.github.io/borg-zoo/).

The first question: **how does better-borg-c compare with the original C
Borg on the same seeds, at each of its milestones and under different
settings, with early-game survival first?**

## How it works

| Piece | What it is |
| --- | --- |
| [Specimens](catalogue/specimens.json) | A Borg version: the game and Borg source at a pinned commit. Today the measured line is **borg-reborn-rs** (the Rust Borg, `diegoami/borg-reborn-rs`, built from a pinned commit: its main and its task branches). The original C Borg (angband/angband `e473720`) and better-borg-c milestones 1–4 are the history. |
| [Profiles](catalogue/profiles.json) | A configuration: the `borg.txt` settings a run uses. Every run checks the settings the Borg actually applied; one that did not take effect makes the run a `config_error`. |
| [Suites](catalogue/suites.json) | Frozen seed lists with a turn cap, time limits and a birth rule. |
| [Experiments](experiments/) | Specimens × profiles × suites, with a control arm for paired comparison. |
| Runner | [better-borg-c](https://github.com/diegoami/better-borg-c)'s native runner and observer, pinned in the specimens catalogue. The zoo calls it; it does not reimplement it. |
| Results | One JSON line per run on the [`results`](https://github.com/diegoami/borg-zoo/tree/results) branch, append-only, one directory per workflow run. |
| Site | Static tables built from the results branch: outcomes per arm, paired rescued/newly-killed counts, survival by turn, depth reached. |

## The current routine (borg-reborn-rs experiments)

A definition in `definitions/NAME.yaml` is the source of an experiment ([docs/DEFINE.md](docs/DEFINE.md)); everything else is generated.

1. **Define.** `python3 -m zoo define definitions/NAME.yaml` writes the specimen, the profiles and `experiments/NAME.json`. Check every setting name exists in the specimen (`git grep NAME COMMIT -- borg-core harness` in borg-reborn-rs; `preflight` does not), and the scary list and plan hashes the specimen pins.
2. **Check.** `python3 -m zoo define --check definitions/*.yaml`, `python3 -m zoo preflight --experiment experiments/NAME.json`, add a shortcut to `catalogue/shortcuts.json` and run `python3 -m zoo.profiles_page` (the page is tested for staleness), then `python3 -m unittest discover -s tests` (about 4 minutes).
3. **Pull request and merge.** A catalogue PR conflicts with every other one that adds entries: take main's `catalogue/*.json` and `docs/PROFILES.md` and re-run `define` and `profiles_page`. Merge after the `test` workflow passes (about 22 minutes; it is slower when the account's 20 concurrent jobs are busy).
4. **Dispatch.** `gh workflow run compare.yml -R diegoami/borg-zoo --ref main -f experiment=experiments/NAME.json -f shards=N`. The input is the **path**, not the name; the experiment file must already be on main; a script that merges and then dispatches must stop if the merge fails. Shards: about 20 games per shard (18 games: 2; 90: 4; 270: 14; 900: 30).
5. **Results.** One directory per run on the `results` branch (`results/EXPERIMENT/RUNID-ATTEMPT/cells.jsonl`). When several runs end together the `collect` step can lose its push (`results -> results (fetch first)`): `gh run rerun RUN --failed` re-runs only that step and the results land under `RUNID-2`. The games are not lost.
6. **Read.** `python3 -m zoo.history` (pooled by study), the gate first (one binary, no config errors, stalls or frozen-turn bursts, every cell accounted for), then per arm and class, paired against the control. Pilots are gates, not results (RULES 14, 16).
7. **Deaths.** The `deaths-*` artifacts of a run (90 days) feed the project skills `/pilot-deaths` and `/death-report` (a written report, or a page with the last recorded screens).

**Suite seeds are frozen.** `classes-1800`, `classes-1800-200k` and `classes-18` are generated by a rule; any change that shifts a seed changes every later start's class (tests pin their hashes). A suite that lists its own seeds must say `"external": true` ([docs/DEFINE.md](docs/DEFINE.md)).

Starting a large experiment is the owner's call (AGENTS.md).

## Running an experiment

On GitHub: **Actions → compare → Run workflow**, then choose the experiment
file. The workflow builds each specimen once, runs the cells in parallel
jobs, appends the results to the `results` branch and rebuilds the site.

A big experiment is better run one arm at a time: `python3 -m zoo arms
--experiment experiments/F.json` lists the arms (`SPECIMEN:PROFILE`), and
each is dispatched with the `arm` input. Every arm run keeps the experiment's
name as its tag and appends its own run to the `results` branch; the site
merges the arm runs of a tag into one experiment page and says where they
differ (date, harness commit, compiler). A timeout then costs one arm, not the
experiment.

**Smoke checks** (a milestone or head builds and plays) live in
[`smoke/`](smoke/), not in `experiments/`. **Actions → smoke → Run workflow**
runs one. The dashboard lists smoke runs, old and new, under its **Smoke** tab
and keeps them out of the comparisons.

Locally (under the shared validation lock if other sessions use this machine):

```sh
git clone https://github.com/diegoami/better-borg-c.git harness
git -C harness checkout "$(python3 -c 'import json;print(json.load(open("catalogue/specimens.json"))["harness"]["commit"])')"
python3 -m zoo build --specimen 4.2.6 --harness harness --out specimens/4.2.6
python3 -m zoo run --experiment smoke/milestones-smoke.json --specimen 4.2.6 \
  --build specimens/4.2.6 --harness harness --work work --out cells/4.2.6.jsonl
python3 -m zoo collect --experiment smoke/milestones-smoke.json --cells cells \
  --results results --run-id local-1
python3 -m zoo site --results results --out _site
```

Tests: `python3 -m unittest discover -s tests`.

## Deaths go to the cemetery

Every natural death of a borg-rs or borg-reborn-rs cell is replayed once with
full logs. Its key stream is checked against the cell's, and the result is
uploaded as a death bundle in the run's `deaths-<specimen>-<shard>` artifacts
(90 days). borg-cemetery imports a run's deaths as replayable dossiers with
`python3 scripts/import_zoo_deaths.py --run RUN_ID`. See
[docs/CEMETERY-DEATHS.md](docs/CEMETERY-DEATHS.md) (#176).

## Cemetery scenarios

[Scenario dispatch](docs/SCENARIO-DISPATCH.md) compares exact pushids on an
immutable Cemetery bank, with separate synthetic reports and complete failure
denominators. The **Scenarios** tab lists scenario runs with their compared
versions, scenario counts, collected cells and paired outcomes. Each run links
to the full report and evidence; synthetic results stay separate from the
population comparisons.

[Balanced999 incidents](docs/BALANCED-INCIDENTS.md) prepares equal111-case
quotas for all nine classes and a bounded saved-state execution in Zoo.

## Reading the results

The Detailed tab lists experiments by the question they ask. Each run starts
with a short comparison brief: versions, settings, baseline, seed count and
turn cap. Background, study plans and exact settings expand on demand.
Reader-facing questions live in `zoo/briefs.py`; add one when introducing an
experiment. The recorded run supplies the conditions, including historical
ones.

The tables are descriptive. Suites are small, intervals are wide, and the
primary endpoint is not yet fixed. "Goal" (alive at the cap having reached
dungeon level 5) is a placeholder until it is. Runs that stall, time out,
crash or fail in the harness are counted and shown, never relabelled as
deaths. Compare arms only within one workflow run: every arm then shares the
compiler, the machine type and the calendar date (the game's seasonal monster
selection depends on the date).

A proposed redesign of storage, long-run resume and the cemetery, shared
with borg-cemetery, is in [docs/data-foundation/](docs/data-foundation/README.md)
(borg-zoo#114; for owner review, not yet adopted).
